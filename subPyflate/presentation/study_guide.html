1. The big picture

1.1 What is this course project asking for?

The HWSW project has two halves, joined at the hip:

  1. Software: pick a benchmark from a fixed list, understand it, profile it, find the slow part, make it faster with concrete measurements. Target: ≥ 7 % improvement.
  2. Hardware: propose a hardware accelerator for the slow part. Write real RTL (SystemVerilog), simulate it in a testbench, describe how software would talk to it (MMIO / DMA / driver), estimate speedup with Amdahl's Law.

Deliverables: a report, a presentation, the source, the AI prompts you used, and everything in a Git repo.

1.2 What benchmark did we pick, and why?

pyflate. It's a pure-Python program that decompresses gzip and bzip2 files. Two reasons it's a good fit:

  • Its slow part is a classic algorithmic problem — a Huffman decoder implemented as a linear scan over Python objects. That gives us a clean software win (canonical Huffman lookup) and a clean hardware kernel (BRAM-backed lookup table).
  • Every commercial DEFLATE / bzip2 hardware decompressor in the world implements exactly this kernel. Our RTL is aligned with real-world designs, not something we invented.

2. Python & interpreters (the reason there's a problem at all)

2.1 What is Python doing under the hood?

When you write x = a + b in Python, CPython (the standard implementation) doesn't turn it into a CPU instruction. It compiles it to bytecode, and the bytecode is executed by a giant function called _PyEval_EvalFrameDefault. That function is a massive switch statement over opcodes: LOAD_FAST, BINARY_ADD, STORE_FAST, etc.

Every one of those opcodes does a lot more than the equivalent C code:

  • Attribute lookups (obj.x) walk the MRO, check descriptors, allocate PyObject boxes.
  • Integer arithmetic boxes int results in PyLong objects on the heap (unless the value falls in the small-int cache −5..256).
  • Every function call sets up a new frame object, argument tuple, and stack.
Why this matters for us Pyflate is pure Python. There is no C extension doing the compression work. Every bit of every decompressed byte flows through _PyEval_EvalFrameDefault. The whole benchmark is essentially "how fast can the CPython interpreter execute this Python loop." Any optimization that reduces the number of bytecodes executed shows up directly as wall-clock time.

2.2 What is python3-dbg?

A debug build of CPython on Debian/Ubuntu. It's compiled without optimizations, with assertions on, and with debug symbols embedded. The debug symbols let tools like perf print human-readable function names in profile output instead of raw hex addresses. The trade-off: it's roughly 2× slower than the release build and its memory allocator does extra bookkeeping (_PyMem_DebugCheckAddress, _PyMem_DebugRawFree) that shows up in our profiles.

2.3 The GIL (Global Interpreter Lock)

CPython lets only one thread execute Python bytecode at a time. Concurrent threads don't parallelize CPU-bound Python code. Pyflate is single-threaded so the GIL doesn't hurt us, but the GIL check (PyGILState_Check) still shows up as a few percent of profile time.

3. Benchmarks & pyperformance

3.1 What is a benchmark?

A benchmark is a small, self-contained program that measures how fast something runs. Good benchmarks are reproducible (same output every time), deterministic (no random noise dominates), and representative (the slow parts of the benchmark match the slow parts of real code).

3.2 pyperformance and pyperf

  • pyperformance is a Python-benchmark suite maintained by the CPython team. It ships ~60 benchmarks and knows how to build isolated virtualenvs, run each benchmark, and print stable timings.
  • pyperf is the low-level timing engine. It handles warm-up iterations, calibration (deciding how many inner iterations to use), and statistical analysis (mean ± std-dev, outlier detection).

Typical run:

python3-dbg -m pyperformance run --bench pyflate

That produces something like:

pyflate: Mean +- std dev: 516 ms +- 29 ms

3.3 Warm-up, values, processes

pyperf uses three levels of repetition:

LevelWhat it isWhy
loopsInner iterations inside one timed measurementMake the timed region big enough that clock resolution doesn't dominate
valuesNumber of measurements per processStatistical noise reduction
processesNumber of fresh Python processesAverages out per-process JIT/warm-up effects

Default non-fast mode: 3 processes × 20 values = 60 measured iterations. --fast: fewer, quicker but less stable.

3.4 The MD5 correctness gate

At the end of every timed iteration, pyflate does hashlib.md5(out).hexdigest() != "afa004a630fe072901b1d9628b960974" and raises if it fails. This means any correctness bug crashes the benchmark. When we optimized, we automatically had a correctness check on every single measurement.

4. Compression 101 — DEFLATE and bzip2

4.1 What is compression?

Compression replaces frequent patterns in a file with shorter codes, and rare patterns with longer codes. The average code length ends up smaller than the raw byte size, so the file shrinks. Decompression is the reverse: turn codes back into original bytes.

4.2 gzip / DEFLATE (RFC 1951)

gzip uses the DEFLATE algorithm. DEFLATE has two ingredients:

  • LZ77: replace repeated substrings with back-references — "the byte pattern at offset X, N bytes long".
  • Huffman coding: replace the resulting literal bytes and back-reference tokens with variable-length prefix codes.

Magic bytes of a gzip file: 0x1f 0x8b.

4.3 bzip2 (used by pyflate's workload)

bzip2 is more elaborate. It stacks four transforms:

  1. Burrows-Wheeler Transform (BWT): shuffle the input so that similar characters cluster. Doesn't compress by itself, but makes subsequent stages much more effective.
  2. Move-to-Front (MTF): replace each byte with the index of that byte in a "recently seen" list, then move it to the front. Turns clusters into low-numbered indices.
  3. Run-Length Encoding (RLE): collapse runs of zeros (very common after MTF) into short markers.
  4. Huffman coding: apply canonical Huffman codes to the resulting symbol stream.

Magic bytes of a bzip2 file: 0x42 0x5a (ASCII "BZ"). The pyflate workload starts with 0x42 0x5a, so only the bzip2 path is exercised. The gzip code path is present in the source but not timed.

Common confusion People sometimes think "bzip2 = gzip but bigger." No — they're completely different algorithms. bzip2 uses BWT + MTF + RLE + Huffman; gzip uses LZ77 + Huffman. They just happen to both produce compressed byte streams.

5. What pyflate actually does, function by function

5.1 The entry point

if __name__ == '__main__':
    runner = pyperf.Runner()
    filename = os.path.join(os.path.dirname(__file__),
                            "data", "interpreter.tar.bz2")
    runner.bench_time_func('pyflate', bench_pyflake, filename)

bench_pyflake(loops, filename) is the timed function. Inside it, a for _ in range(loops) loop opens the file, wraps it in an RBitfield (MSB-first bit reader), reads two bytes of magic, and dispatches to gzip_main or bzip2_main. When the loop ends, it takes MD5 of the last output and asserts.

5.2 Bitfield and RBitfield

These are the bit readers. They wrap a byte-oriented file and let the caller ask for arbitrary numbers of bits at a time.

  • Bitfield is LSB-first (used by gzip / DEFLATE — bits within a byte are read low-to-high).
  • RBitfield is MSB-first (used by bzip2 — bits within a byte are read high-to-low).

Both expose two methods used everywhere:

  • snoopbits(n): look at the next n bits without consuming them.
  • readbits(n): return the next n bits and advance.

5.3 HuffmanTable and HuffmanLength

A Huffman table is a Python list of HuffmanLength objects sorted by bit-length. Each entry stores (code, bits, symbol, reverse_symbol). The critical method is: 

def find_next_symbol(self, field, reversed=True):
    cached_length = -1
    cached = None
    for x in self.table:
        if cached_length != x.bits:
            cached = field.snoopbits(x.bits)
            cached_length = x.bits
        if (reversed and x.reverse_symbol == cached) or \
           (not reversed and x.symbol == cached):
            field.readbits(x.bits)
            return x.code
    raise Exception("unfound symbol")

This is a linear scan over the whole table for every symbol emitted. If the table has 200 entries and the block emits a million symbols, that's 100 million Python attribute reads. This is our bottleneck.

5.4 decode_huffman_block — the timed hot loop

Rough structure inside one bzip2 block:

while True:
    r = t.find_next_symbol(b, False)   # <-- called millions of times
    if 0 <= r <= 1:
        # accumulate RLE repeat count for RUN symbols
    elif r == symbols_in_use - 1:
        break                           # end of block
    else:
        buffer.append(favourites[r - 1])
        move_to_front(favourites, r - 1)   # <-- also hot

Then, once the block ends, bwt_reverse(joined_buffer, pointer) inverts the Burrows-Wheeler transform and a byte-level RLE pass writes the decompressed bytes to out.

5.5 move_to_front, bwt_transform, bwt_reverse

move_to_front(l, c) is a Python one-liner that rotates the element at index c to position 0:

def move_to_front(l, c):
    l[:] = l[c:c+1] + l[0:c] + l[c+1:]

Three slice allocations every call. Elegant but not fast.

bwt_transform builds an index array called base for the inverse BWT. The original does:

F = bytes(sorted(L))
base = []
for i in range(256):
    base.append(F.find(int2byte(i)))    # 256 linear scans

256 bytes.find calls, each O(N) where N can be ~900 000 bytes. That's ~230 million byte comparisons per bzip2 block — pure C-level work but not free.

6. Huffman coding, deeply

6.1 The core idea

David Huffman's 1952 algorithm builds a binary tree where each leaf is a symbol. Frequent symbols end up near the root (short codes); rare symbols end up deep (long codes). The tree has the prefix property: no code is a prefix of another, so a stream of concatenated codes can be decoded without markers.

Example: for symbols A, B, C, D, E with frequencies (5, 4, 3, 2, 1):

              (15)
             /    \
           (9)    (6)
          /  \   /  \
        (5) (4) (3) (3)
         A   B   C  / \
                  (2) (1)
                   D   E

Codes: A=00  B=01  C=10  D=110  E=111

6.2 Canonical Huffman codes

For a decoder you don't need the tree structure — only the bit-length of every symbol. Given the lengths, canonical form assigns codes in a deterministic way: sort symbols by length, assign the first N-bit code as 0…0, increment for each subsequent code of the same length, left-shift when the length increases.

Our example, canonical order (bits, symbol) = (2,A), (2,B), (2,C), (3,D), (3,E):

A: code = 00
B: code = 01     (A+1)
C: code = 10     (B+1)
D: code = 110    (C+1) << 1
E: code = 111    (D+1)

This is exactly what HuffmanTable.populate_huffman_symbols computes.

6.3 The two ways to decode

  1. Linear scan (what pyflate ORIGINALLY does): for every incoming bit stream, iterate over the table; for each unique bit-length, snoop that many bits and check against x.symbol or x.reverse_symbol. O(#codes) per symbol.
  2. Lookup table (what our OPTIMIZED version does): snoop MAX_BITS bits (where MAX_BITS = the longest code in the table). Use those bits as an index into a precomputed table of size 2^MAX_BITS. Each entry stores (symbol, code_length). Consume code_length bits from the stream. O(1) per symbol.

Why the LUT works — the key trick

When you snoop MAX_BITS bits, a short code (say 2 bits) sits in only part of those MAX_BITS. The remaining MAX_BITS - 2 bits are whatever comes next in the stream — the suffix. For a code of length bits, the same code plus every possible suffix would produce 2^(MAX_BITS-bits) different snoop values, all of which should decode to the same symbol.

So when we build the LUT we fill all 2^(MAX_BITS-bits) matching slots with the same (symbol, code_length) entry. Then a single lookup gets us the right answer no matter what the suffix bits happen to be.

Why this is the hardware kernel Every real DEFLATE / bzip2 hardware decompressor implements exactly this: a small BRAM (block RAM inside an FPGA) filled with the LUT entries, and a barrel-shifter feeding it MAX_BITS bits per cycle. Because MAX_BITS ≤ 15 for DEFLATE, the LUT fits in ~64 KB — one or two BRAMs.

7. Profiling tools — perf, py-spy, flame graphs

7.1 The generic idea of a profiler

A profiler answers "where does my program spend its time?" There are two families:

  • Sampling profilers interrupt the program periodically (e.g. 999 times a second) and record the call stack at that instant. If a function takes 30 % of runtime, ~30 % of samples land in it.
  • Instrumenting profilers insert counters around every function entry/exit. More accurate but slow the program down a lot.

We use sampling profilers because pyflate finishes quickly and instrumenting overhead would distort the picture.

7.2 perf (Linux only)

perf is a Linux kernel tool. It reads two things:

  1. Software events from the kernel scheduler: task-clock, cpu-clock, page-faults, context-switches, cpu-migrations. Always available.
  2. Hardware events from the CPU's Performance Monitoring Unit (PMU): cycles, instructions, branches, branch-misses, cache-references, cache-misses. Require direct hardware access — disabled inside most VMs.

Three modes we use:

# count events across many runs
perf stat -r 3 -e task-clock,cpu-clock,cycles,instructions ... -- 

# sample call stacks at 999 Hz
perf record -F 999 -g -o out.data -- 

# read back the samples grouped by function
perf report --stdio -i out.data > report.txt

7.3 py-spy

py-spy is a Rust binary that reads a running Python process's memory and reconstructs its Python call stack. Unlike perf, it works on Windows too (that's how we generated flame graphs on your laptop). It produces SVG flame graphs directly.

7.4 Flame graphs

Brendan Gregg's visualization: each bar is a function. The width of the bar is how much time was spent in that function or its callees. The height is how deeply nested it is. Wide bars = big cost. Tall thin bars are just deeply nested but not necessarily costly.

Our five flame graphs (flamegraph_pyspy_{baseline,attempt1,attempt2,attempt3,final}.svg) drop from 6847 samples (baseline) to 4984 (final) over the same workload — visual confirmation of the ~30 % speedup.

Common exam trap "Flame graph width is the percentage of time" — almost. It's the percentage of sampled time. If your total runtime dropped 30 %, a function that keeps its width didn't get slower; the rest of the program just got faster. Always cross-check against absolute wall-clock time.

8.2 Interpretation

The interpreter loop tops the list because everything in Python runs through it. But underneath, three cost patterns stand out:

  1. Object churn (list_dealloc, MTF slices, tuple lookups) — created by the algorithms operating on Python-level objects.
  2. Integer boxing (PyLong_New) — readbits/snoopbits do lots of small arithmetic; each result becomes a heap-allocated PyLong.
  3. Debug allocator overhead — real deployments wouldn't use python3-dbg, so this is inflated; we mention but don't attack it.

8.3 The one function to attack

Adding perf report's evidence to the code inspection: HuffmanTable.find_next_symbol is the algorithmic bottleneck. It's called once per emitted symbol and does an O(#codes) Python scan. The interpreter cost that shows up in _PyEval_EvalFrameDefault is largely caused by this function. Replace it and everything else drops proportionally.

9. The three optimization attempts

Attempt discipline Each attempt makes exactly one focused change. This lets us blame or revert single ideas, and gives the graders a clean before/after per idea.

9.1 Attempt 1 — Canonical Huffman lookup table

Target: the linear scan in find_next_symbol.

We add a method that builds a lookup table of size 2^max_bits and caches it on the HuffmanTable instance. Two directions:

  • reversed=True (gzip / LSB-first Bitfield): bits are read low-to-high, so the code sits in the LOW bits of the snoop value. LUT index formula: lut[(suffix << bits) | reverse_symbol] = (code, bits).
  • reversed=False (bzip2 / MSB-first RBitfield): bits are read high-to-low, so the code sits in the HIGH bits of the snoop value. LUT index formula: lut[(symbol << (max_bits - bits)) | suffix] = (code, bits).

The new find_next_symbol:

def find_next_symbol(self, field, reversed=True):
    attr = "_lut_rev" if reversed else "_lut_fwd"
    lut = getattr(self, attr, None)
    if lut is None:
        lut = self._build_lut(reversed); setattr(self, attr, lut)
    try:
        code, bits = lut[field.snoopbits(self.max_bits)]
    except Exception:
        return self._fallback_scan(field, reversed)   # true EOF safety
    if code < 0:
        return self._fallback_scan(field, reversed)   # empty slot
    field.readbits(bits)
    return code

Correctness risk: zero if the LUT is built right. The fallback covers the rare edge case where snoopbits(max_bits) throws at end-of-stream before a shorter code would have matched.

9.2 Attempt 2 — MTF, BWT, and int2byte cleanup

Three surgical changes stacked on Attempt 1:

# before
def move_to_front(l, c):
    l[:] = l[c:c+1] + l[0:c] + l[c+1:]

# after
def move_to_front(l, c):
    if c:
        l.insert(0, l.pop(c))

Same asymptotic O(N), but no temporary slice objects.

# before  (256 whole-block scans)
F = bytes(sorted(L))
base = [F.find(int2byte(i)) for i in range(256)]

# after  (one pass + cumulative sum)
counts = [0]*256
for c in L: counts[c] += 1
base = [0]*256
total = 0
for i in range(256):
    base[i] = total if counts[i] else -1
    total += counts[i]

The -1 sentinel matches the original's bytes.find return value for missing bytes.

# precomputed byte-to-bytes table replaces struct.pack per call
_INT2BYTE = tuple(bytes((i,)) for i in range(256))

9.3 Attempt 3 — Hot-loop attribute hoisting

Python attribute reads (e.g. favourites.pop) do a dict lookup on the object. In a tight loop that adds up. We hoist them to local variables:

while True:
    ...
    r = t_find(b, False)                # was t.find_next_symbol
    if 0 <= r <= 1:
        ...
    elif repeat > 0:
        buffer_append(favourites[0] * repeat)   # was buffer.append
        repeat = 0
    if r == end_symbol:
        break
    else:
        idx = r - 1
        o = favourites[idx]
        if idx:
            favourites_insert(0, favourites_pop(idx))
        buffer_append(o)

Also the byte-RLE decode uses direct integer indexing into the bytes object (no per-byte slicing) with the precomputed _INT2BYTE table.

9.4 Final = Attempt 3

subPyflate/optimized/final/ is a copy of Attempt 3. Rationale: it strictly layers all three optimizations, and both the Windows pyperformance run (+29.84 %) and the VM perf run (+41.10 %) confirm it as the fastest correct choice.

10.5 The "Attempt 1 alone is a regression" finding

Our custom cold-loop benchmark (scripts/windows_bench.py) showed Attempt 1 slower than baseline by 32 %. Reason: _build_lut is a Python for loop that fills up to 2^max_bits entries (≈ 131 000 for max_bits=17) per Huffman group. On short workloads the build cost dominates the per-symbol savings.

Under pyperformance's warmed-up methodology the same code shows +16 % because the LUT-build cost is amortized across many timed iterations. Both are true; they measure different aspects of the same optimization.

This finding strengthens the hardware story: BRAM has O(1) load and O(1) lookup with no interpreter overhead on either axis.

11. Why hardware?

11.1 Where the Python-side wins run out

Even after all three optimizations, the interpreter tax on Python is unavoidable. Each symbol still passes through _PyEval_EvalFrameDefault. There's no way to write pure Python that gets faster than one opcode per emitted symbol.

11.2 Hardware removes the whole interpreter

An FPGA can execute the canonical Huffman lookup in one clock cycle (with pipelining, potentially one symbol per clock). No opcode dispatch, no attribute reads, no garbage-collected boxes. The same algorithm we discovered in software becomes 100–1000× faster in hardware because it's not running through an interpreter.

11.3 Why this specific kernel

Three reasons Huffman decoding is a natural hardware target:

  • The data-flow is fixed — snoop, look up, consume. No branches on the actual data.
  • The state is tiny — a bit buffer, a symbol counter, a small FSM.
  • The lookup table maps beautifully onto FPGA block RAM (BRAM). One BRAM tile = ~36 kbit = enough for a MAX_BITS=15 table.

12. The accelerator design

12.1 The three modules

huff_lut.sv — the memory

A synchronous BRAM-shaped block. One write port lets the CPU upload the canonical Huffman table one entry at a time before decode starts. One read port lets the decoder query the LUT during decode. Each entry is {code_bits[4:0], symbol[15:0]} — 21 bits, padded to 32 for BRAM friendliness. Depth = 1 << MAX_BITS.

bit_shifter.sv — the bit reader

A rolling buffer that mirrors the software RBitfield:

  • Accepts a new byte per cycle when can_accept_byte is high; new byte enters the LOW 8 bits, old bits shift UP by 8 (matches RBitfield's _more()).
  • Exposes snoop — the top MAX_BITS bits of the valid buffer contents.
  • Accepts consume per cycle — drops that many bits from the top.

Combinational path (single cycle): the same clock edge can consume old bits AND absorb a new byte, matching what pyflate does in software when readbits triggers needbits.

huffman_decoder.sv — the FSM

Four states:

  1. S_IDLE: wait for start. On start, latch max_symbols and flush the shifter.
  2. S_ISSUE: when snoop_ready is high (buffer has ≥ MAX_BITS bits), assert LUT read enable with rd_addr = snoop.
  3. S_WAIT: wait one cycle for the LUT synchronous read to return (symbol, code_bits). If code_bits == 0, latch error and go idle.
  4. S_CONSUME: assert bs_consume = code_bits, pulse symbol_valid. Decrement symbols_left. If zero, pulse done and go idle; else back to S_ISSUE.

Throughput: 1 symbol every 3 clocks in this v1. A pipelined v2 (registering the snoop, folding WAIT into ISSUE) could hit 1 symbol per clock. That improvement is documented as future work in docs/13_hardware_performance.md.

13. SystemVerilog RTL walkthrough

13.1 SystemVerilog crash course

  • module: reusable block with named ports.
  • logic: signal type (like wire or reg, but modern).
  • always_ff @(posedge clk): describes flip-flops. Assignments here are <= (non-blocking) and take effect at the next clock edge.
  • always_comb: describes combinational logic (no state). Assignments are = and are re-evaluated whenever inputs change.
  • parameter: compile-time constant that can be overridden when the module is instantiated.
  • typedef enum: names for FSM state values.

13.2 huff_lut.sv annotated

module huff_lut #( parameter int MAX_BITS = 15, ...) (
    input  logic clk, rst_n,
    input  logic wr_en, [MAX_BITS-1:0] wr_addr, ...,   // write port
    input  logic rd_en, [MAX_BITS-1:0] rd_addr,        // read port
    output logic [SYMBOL_WIDTH-1:0] rd_symbol,
    output logic [CODE_BITS_W-1:0]  rd_bits,
    output logic rd_valid);

    logic [ENTRY_W-1:0] mem [0:DEPTH-1];   // this array becomes BRAM

    always_ff @(posedge clk or negedge rst_n) begin
        if (!rst_n) rd_valid_q <= 0;
        else begin
            rd_valid_q <= 0;
            if (wr_en) mem[wr_addr] <= {wr_bits, wr_symbol};
            if (rd_en) begin
                rd_data_q  <= mem[rd_addr];
                rd_valid_q <= 1;
            end
        end
    end
    ...
endmodule

Key point: the read is registered — data appears one cycle after rd_en. That's why the FSM has a separate S_WAIT state.

13.3 bit_shifter.sv — the tricky masking

always_comb begin
    if (consume != 0 && !under_run) begin
        bits_after_consume = bits_q - consume;
        buf_after_consume  = buffer & ((ONE << bits_after_consume) - ONE);
    end else begin
        bits_after_consume = bits_q;
        buf_after_consume  = buffer;
    end
end

(ONE << bits_after_consume) - ONE is a mask of the low bits_after_consume bits set. ANDing zeroes out the bits we consumed from the top. In the flip-flops we then maybe shift a new byte in: 

always_ff @(posedge clk or negedge rst_n) begin
    if (!rst_n || flush) begin buffer <= 0; bits_q <= 0; end
    else if (byte_valid && (bits_after_consume + 8) <= BUF_W) begin
        buffer <= (buf_after_consume << 8) | byte_data;
        bits_q <= bits_after_consume + 8;
    end else begin
        buffer <= buf_after_consume;
        bits_q <= bits_after_consume;
    end
end

13.4 huffman_decoder.sv — the FSM in one page

Standard 2-block FSM (combinational state_n + sequential state):

always_comb begin
    state_n = state;                       // default hold
    /* default all outputs */
    case (state)
        S_IDLE:    if (start)         state_n = S_ISSUE;
        S_ISSUE:   if (snoop_ready)   begin lut_rd_en=1; state_n=S_WAIT; end
        S_WAIT:    if (lut_rd_valid) begin
                      if (lut_rd_bits == 0) begin error=1; state_n=S_IDLE; end
                      else state_n = S_CONSUME;
                   end
        S_CONSUME: begin
                      bs_consume   = lut_rd_bits;
                      symbol_valid = 1;
                      if (symbols_left_q == 1) begin done=1; state_n=S_IDLE; end
                      else state_n = S_ISSUE;
                   end
    endcase
end
always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) state <= S_IDLE; else state <= state_n;

14. Testbenches & verification

14.1 What a testbench does

A testbench is not part of the chip. It's a Verilog program that drives the design (the DUT — Device Under Test), checks its outputs against an expected reference, and prints PASS/FAIL. Every module we wrote has a matching testbench under hw/tb/.

14.2 The three testbenches

tb_huff_lut.sv

Writes 5 entries at random addresses, reads each back one cycle later, asserts exact match. Coverage: does the storage work?

tb_bit_shifter.sv

Maintains an in-testbench software mirror of the shifter (a scalar buffer). On every push/consume, compares the DUT's snoop and bits_avail against the mirror. Coverage: does the bit math match RBitfield's exact semantics under every combination of push, consume, and buffer fill level?

tb_huffman_decoder.sv — the end-to-end test

Builds this canonical Huffman table (5 symbols, max_bits = 3):

SymbolBitsCode (MSB-first)
0200
1201
2210
33110
43111

Encodes the reference message [0, 1, 2, 3, 4, 0, 4, 1]:

00 01 10 110 111 00 111 01 = 19 bits = padded to 3 bytes = 0x1B 0x73 0xA0.

Loads the LUT via the write port, drives those three bytes into the shifter, calls start, collects the emitted symbols, compares against the reference — all 8 symbols must match exactly.

14.3 The simulator

Icarus Verilog 12.0 on Windows. Command per testbench:

   for each Huffman group:
       load LUT (2^MAX_BITS writes)
       set MAX_SYMBOLS

15.3 What "proposed" means

The RTL is implemented and simulated. The MMIO wrapper, DMA engine, AXI4-Lite bus adapter, Python C-extension driver, and real FPGA integration are documented on paper (docs/12_hw_sw_interface.md) but not implemented. This is the same boundary the raytrace subproject drew.

16. Amdahl's Law & estimated speedup

16.1 The formula

If a fraction P of the total runtime is accelerated by a factor S, the overall speedup is:

Speedup = 1 / ( (1 − P) + P/S )

Two intuitions from this:

  • If P is small, even S → ∞ can't help much. That's why we pick a hotspot.
  • If P is close to 1, the achievable speedup approaches S.

16.2 Applied to our case

Suppose P = 0.40 (the fraction of runtime inside the Huffman inner loop) and S = 10 (the accelerator runs the per-symbol work 10× faster than pure Python):

Speedup = 1 / (0.60 + 0.40/10) = 1 / 0.64 ≈ 1.56×
Improvement = (1 − 1/1.56) × 100 ≈ 36 %

17. Environment — VM, TCG, WHPX, and why we care

17.1 What is QEMU?

QEMU is a machine emulator. It can run an entire operating system (a "guest") inside a program on your host. It emulates CPU, RAM, disks, network — everything a real machine has.

17.2 Acceleration backends

  • KVM (Linux): uses the host's CPU virtualization instructions. Near-native speed. Requires Linux and /dev/kvm.
  • WHPX (Windows Hypervisor Platform): the Microsoft equivalent. Requires Hyper-V and administrator access to enable. Also near-native speed when it works.
  • TCG (Tiny Code Generator): pure software emulation. Doesn't need hardware virtualization. Roughly 10–20× slower than native.

17.3 What we used and why

The final measurement environment is the course-provided QEMU guest on naranja4 (CS-lab server), launched by Sari's tmux session with -cpu host,pmu=on -accel kvm. That means near-native speed AND hardware PMU counters exposed to the guest — which is exactly what perf stat -e instructions,branches,cache-references needs.

Earlier in the project we also ran a local QEMU on the Windows box using TCG (software emulation). That worked for wall-clock timing and software events, but was ~10-20× slower and couldn't expose hardware PMU counters (TCG doesn't emulate the CPU's PMU). The CS-lab KVM run is the one to present as "official" — hardware counters and near-native performance.

17.4 Why the cycles counter still shows 0 (on KVM)

Even under KVM with pmu=on, the naranja4 Xeon E5-2630 v3 host doesn't expose the specific cycles PMU event to the guest. All OTHER hardware counters (instructions, branches, branch-misses, cache-references, cache-misses) ARE exposed and captured cleanly. The raytrace team hit the exact same quirk on the CS-lab VM and just documented it (cpu-cycles=0 because the PMU cycle counter was unavailable in this environment). We do the same — we have plenty of hardware evidence without the cycles counter.

19. Q&A prep — 30+ questions the instructor might ask

Q1. What does pyflate do?
It's a pure-Python decompressor for gzip and bzip2 files by Paul Sladen. The pyperformance benchmark exercises the bzip2 path on a fixed compressed file and MD5-checks the output.
Q2. Why did you pick pyflate?
Different from raytrace (compression instead of geometry) and it has a clean algorithmic hotspot (the Huffman inner loop) that maps to a well-understood hardware kernel — a canonical Huffman LUT decoder.
Q3. How did you measure the baseline?
Two ways. On the VM: sudo perf stat -r 3 -- python3-dbg -m pyperformance run --bench pyflate --fast. On Windows: python -m pyperformance run --bench pyflate non-fast (60 iterations after warmup).
Q4. Why pyperformance?
It's the standard Python-benchmark harness. It uses pyperf internally to calibrate loop counts, handle warmup, run multiple processes for noise averaging, and print stable mean ± std-dev output.
Q5. What does perf actually measure?
Samples the CPU program counter (and, with -g, the call stack) at a fixed rate — we used 999 Hz. Also counts kernel events like task-clock, page-faults, and hardware PMU events like cycles and instructions when they're available.
Q6. What does py-spy tell us that perf doesn't?
py-spy walks Python's own call stack directly, so it shows Python function frames like bench_pyflake → bzip2_main → decode_huffman_block → find_next_symbol. perf tends to bottom out in interpreter internals unless you carefully match Python debug symbols.
Q7. How do you read a flame graph?
Bars are functions. Width = sampled runtime share (not absolute time). Height = call-stack depth. Wide bars = hotspots. Tall thin bars = deep call chains that are cheap individually.
Q8. Why does _PyEval_EvalFrameDefault keep the top slot after optimization?
It's the CPython opcode dispatcher — every Python opcode passes through it. In a pure-Python workload it's necessarily on top. Its relative share stays around 20 %; its absolute time drops proportionally with total runtime.
Q9. How did you confirm the bottleneck?
Code inspection identified HuffmanTable.find_next_symbol as an O(#codes) Python scan called per emitted symbol. perf report showed the interpreter time it caused; py-spy confirmed the call chain visually.
Q10. What optimization did you apply?
Three layered: (1) canonical Huffman lookup table indexed by snoopbits(max_bits); (2) MTF using pop/insert instead of slice, BWT with single-pass counts, precomputed _INT2BYTE table; (3) hot-loop attribute hoisting to locals and byte-indexed RLE decode.
Q11. Walk me through the LUT idea.
Every canonical Huffman code is a prefix of the next MAX_BITS bits. Snoop MAX_BITS bits, use them as an index into a precomputed table sized 2^MAX_BITS. Each entry stores (symbol, code_bits); short codes are replicated across their matching suffixes. One lookup replaces the linear scan.
Q12. What if a Huffman table has an unused code slot?
Its LUT entry has code_bits = 0. On lookup we fall back to the original linear scan. In practice this only happens at true end-of-stream.
Q13. How did you verify correctness?
scripts/check_attempt_correctness.py loads the preserved original and the attempt as modules, decompresses the same workload with both, does byte-for-byte comparison, and MD5-checks against afa004a630fe072901b1d9628b960974. All four attempts show IDENTICAL=YES.
Q14. What are the official before/after numbers?
VM: 1257 s → 740 s = +41.10 %. Windows pyperformance: 516 ms → 362 ms = +29.84 %. Both above 7 %.
Q15. Why do the VM and Windows numbers differ?
Windows uses release CPython 3.12; VM uses python3-dbg 3.10 with debug allocator overhead. Absolute times differ; the improvement percentage is real in both.
Q16. Attempt 1 alone showed a regression in one measurement. Why?
The LUT builder is a Python for loop that fills up to 2^max_bits entries per Huffman group. On short cold-loop measurements the build cost swamps the per-symbol savings. Under pyperformance's warmed-up methodology it becomes a clean +16 % win because the build amortizes across many timed iterations. This finding actually strengthens the hardware argument.
Q17. Why does the hardware argument get stronger from that?
Hardware BRAM has O(1) LOAD and O(1) LOOKUP. Software Python has O(1) lookup but O(2^max_bits) load. The regression shows that build cost is real and Python-specific — hardware removes it entirely.
Q18. Why is Huffman decoding a good hardware target?
Fixed data-flow (snoop → look up → consume), tiny state (bit buffer + counter + FSM), lookup table fits in one FPGA BRAM. Every commercial DEFLATE/bzip2 decompressor implements exactly this piece in hardware.
Q19. Describe the accelerator's three modules.
huff_lut — BRAM-shaped canonical Huffman table with one write port (CPU loads) and one read port (decoder queries). bit_shifter — MSB-first rolling buffer mirroring RBitfield, exposes snoop and consume. huffman_decoder — 4-state FSM (IDLE→ISSUE→WAIT→CONSUME→ISSUE) tying them together, counts down max_symbols.
Q20. What's the throughput of your accelerator?
v1: 1 symbol per 3 clocks (ISSUE + WAIT + CONSUME). A pipelined v2 (documented as future work) can hit 1 symbol per clock by registering snoop on the LUT read port and folding WAIT into ISSUE.
Q21. What clock frequency did you target?
200 MHz (ESTIMATE). No synthesis was run. Small BRAM + short combinational paths + a tiny FSM make this a conservative target for a modern FPGA.
Q22. Did you actually simulate the RTL?
Yes. Icarus Verilog 12.0 on Windows. Three self-checking testbenches: tb_huff_lut (5 checks), tb_bit_shifter (8 checks), tb_huffman_decoder (9 checks including an end-to-end 8-symbol decode with a hand-crafted canonical table). All 22 checks pass, logs in hw/results/.
Q23. Did you synthesize? Do you know real area/power?
No synthesis was run. All hardware performance, area, and power figures in docs/13_hardware_performance.md are explicitly labeled ESTIMATE. This matches the raytrace subproject's evidence-boundary policy.
Q24. Explain your HW/SW interface.
Proposed AXI4-Lite MMIO register bank: CTRL, STATUS, MAX_SYMBOLS, TABLE_ADDR, TABLE_DATA, INPUT_FIFO, OUTPUT_FIFO. Byte stream in and symbol stream out over AXI-Stream. Python C-extension driver would expose the accelerator as a drop-in replacement for HuffmanTable.find_next_symbol. All PROPOSED, not implemented in v1.
Q25. What is the communication overhead?
Per Huffman group: one LUT upload (2^max_bits writes, up to ~32K cycles ≈ 160 µs at 200 MHz — amortized over ~1 M symbols per block). Steady state: 8-bit byte in and 21-bit symbol out per decode. Well under AXI-Stream bandwidth at 200 MHz.
Q26. Amdahl's Law — what's your projected system speedup?
At S=10 and P≈0.4, Speedup = 1/(0.6 + 0.04) ≈ 1.56× (~36 % improvement). At S=20, ≈ 1.61×. All ESTIMATES with the assumed P from profiling.
Q27. What about hardware counters? Your perf stat shows <not supported>.
TCG software emulation doesn't emulate the CPU's PMU, so hardware counters (cycles, instructions, branches, branch-misses, cache) show <not supported>. Documented in the report and in docs/03_profiling.md. Same limit Sari noted for WHPX and the raytrace team saw on the CS-lab VM. Software counters (task-clock, page-faults) captured cleanly.
Q28. Why did you use a local QEMU instead of the CS-lab VM?
CS-lab account was blocked by a password reset over the Yom Kippur holiday. We booted the same Ubuntu 22.04 Jammy cloud image locally in QEMU on Windows — the exact image the course provides — and ran everything there. Environment is identical from perf's perspective; only the accelerator underneath differs.
Q29. What did you preserve from the original benchmark?
The full source at original/bm_pyflate/run_benchmark.py, byte-identical to the pyperformance shipped file, and its pyproject.toml. Nothing in original/ was modified.
Q30. How would you validate the hardware in reality?
Synthesize the RTL for a target FPGA, run place-and-route, get real timing (clock frequency) and area. Build the MMIO wrapper. Implement the driver. Run pyflate with the hardware in the loop and compare wall-clock. All out of this project's scope but documented as remaining work in reports/report_pyflate.md §18.
Q31. If communication overhead dominates, what saves you?
Amortization. The LUT upload is O(2^max_bits) but happens once per Huffman group; a group emits O(10^6) symbols, so per-symbol upload cost approaches zero. AXI-Stream at 200 MHz delivers 200 MB/s peak — the decoder consumes bytes at 66 MB/s (v1) or 200 MB/s (v2), so stream bandwidth isn't the bottleneck either.
Q32. What parts of your presentation are MEASURED versus ESTIMATED?
MEASURED: wall-clock times (VM + Windows), correctness (MD5), RTL simulation results. ESTIMATED: hardware clock frequency, throughput, Amdahl speedup, area, power. PROPOSED (not built): MMIO/DMA/driver.

20. 2-minute & 30-second summaries

20.1 Two-minute summary

Pyflate is a pure-Python bzip2 decoder benchmarked by pyperformance. Its profiled hotspot is HuffmanTable.find_next_symbol, which does an O(#codes) Python scan over table entries for every emitted symbol. We attacked it in three layered attempts. Attempt 1 replaces the scan with a canonical Huffman lookup table indexed by the next MAX_BITS bits — one BRAM lookup per symbol instead of a linear scan. Attempt 2 stacks three constant-factor fixes: move-to-front using pop/insert (no slice allocations), BWT inverse using a single-pass frequency count instead of 256 whole-block scans, and a precomputed int-to-byte table replacing per-call struct.pack. Attempt 3 hoists every attribute lookup in the tight loop to locals and uses direct integer indexing into the post-BWT bytes object. Each attempt is proven correct by byte-for-byte comparison plus the pyflate MD5 gate afa004a630fe072901b1d9628b960974 — all four pass. Official measurements: 1257 s → 740 s on the VM (+41.10 %), 516 ms → 362 ms on Windows pyperformance (+29.84 %), both well above the 7 % target. The same canonical Huffman decoder becomes the hardware accelerator: three SystemVerilog modules — a BRAM-backed LUT, an MSB-first rolling bit shifter mirroring RBitfield, and a four-state FSM tying them together. All 22 testbench checks pass under Icarus Verilog. Hardware performance figures are Amdahl estimates (~1.56× at P=0.4, S=10). MMIO / AXI-Stream / driver are proposed, not implemented. Every claim traces to a saved artifact under results/, profiling/, or hw/results/.

20.2 Thirty-second summary

We optimized pyflate's O(#codes) Huffman scan with a canonical Huffman lookup table plus a few constant-factor cleanups. Verified correct; +41 % faster on the VM (perf stat + python3-dbg), +30 % on Windows (pyperformance). Same algorithm implemented as a small SystemVerilog accelerator — three modules, 22/22 simulation checks pass under Icarus. Hardware performance is an Amdahl estimate; the driver and MMIO wrapper are proposed, not built.
