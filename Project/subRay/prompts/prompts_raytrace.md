## 3. RAYTRACE SOFTWARE OPTIMIZATION

### Prompt 10 — Create the optimization plan

For each software candidate, document:
- measured bottleneck being targeted,
- original behavior,
- proposed change,
- expected mechanism for speedup,
- effect on function calls, allocations, lookups, and interpreter work,
- correctness risks,
- how correctness will be checked,
- how performance will be measured.

Rank the candidates.

The main candidate should target the object-heavy `Vector`/`Point`/`Ray` geometry path by replacing repeated temporary objects and method calls with scalar local computations while preserving output.

### Prompt 11 — Optimization Attempt 1: scalarize the hot geometry path

Create `Project/subRay/optimized/attempt1/` from the preserved original.

Rewrite the hottest geometry/render/shading path to use scalar local floats and tuple-style scene data where possible, reducing:
- temporary `Vector`, `Point`, and `Ray` objects,
- method dispatch,
- attribute/type lookup,
- Python object churn.

Do not change the mathematical result.

Create an external correctness check that renders the same fixed scene for original and optimized versions and compares the output byte-for-byte / by SHA256.

Only after correctness passes, collect a preliminary performance measurement and profile Attempt 1.

### Prompt 12 — Optimization Attempt 2: local lookup/alias hoisting

Re-profile Attempt 1 and inspect remaining Python interpreter overhead.

Create `Project/subRay/optimized/attempt2/`.

Hoist stable global/helper lookups into local variables inside the hottest functions, especially `ray_colour()` and the benchmark/render loop where justified.

Do not combine unrelated changes.

Verify the rendered output remains identical, benchmark the attempt, and preserve it even if it is slower than Attempt 1.

### Prompt 13 — Optimization Attempt 3: reduce visibility-call/frame overhead

Re-profile the optimized version and inspect remaining call/frame overhead in the shading path.

Create `Project/subRay/optimized/attempt3/`.

If justified, inline the per-light visibility test inside the Lambert loop to eliminate repeated `visible_light()` call/frame creation while preserving:
- the same sphere/plane tests,
- the same shadow visibility semantics,
- the same floating-point behavior needed for the tested scene.

Verify output identity before measuring.

### Prompt 14 — Select and lock the final Raytrace software version

Compare all correct attempts.

Record each version’s correctness and measured timing. Keep all attempts in the repository.

Use the version chosen by the official project pipeline as `Project/subRay/optimized/final/`.

The official submission was locked to Attempt 1 because it introduced the dominant scalarization speedup and the official before/after pipeline was generated from it, even though a later non-fast perf-stat comparison showed Attempt 3 slightly faster.

Run matched official original/final measurements and save:
- `results/original_official.txt`,
- `results/final_official.txt`,
- `reports/final_performance_comparison.txt`.

Compute speedup and percentage improvement, and state whether the project’s 7% target is achieved.

### Prompt 15 — Compare original and final profiling

Collect matched-methodology baseline/final profiling where possible.

Compare:
- perf stat counters,
- perf report symbol shares,
- matched full-suite flame graphs,
- total sample counts.

Explain that relative percentages can rise even while absolute runtime falls. In particular, if `_PyEval_EvalFrameDefault` becomes a larger percentage of the final run, do not call that a regression if wall-clock time, instruction count, and total samples fall substantially.

Treat the py-spy graphs as supplemental if they are dominated by pyperf manager/worker-control frames or were captured without subprocess following.

## 4. RAYTRACE HARDWARE ACCELERATION

### Prompt 16 — Choose the hardware accelerator boundary

Use the final profiling and the repeated geometry structure of Raytrace to compare hardware candidates:
- dot-product/vector arithmetic unit,
- normalization/reflection unit,
- single ray/object intersection unit,
- whole-scene sphere/plane intersection + nearest-hit reduction accelerator.

Consider:
- frequency of use,
- arithmetic density,
- parallelism,
- pipelining,
- object count,
- communication overhead,
- number of software/hardware crossings.

Choose the whole-scene intersection/closest-hit kernel, also supporting visibility/shadow tests, because it groups a large repeated arithmetic workload behind one interface.

### Prompt 17 — Design the Raytrace intersection accelerator

Create a hardware architecture document for the selected kernel.

Define:
- ray origin/direction inputs,
- sphere and plane scene inputs,
- mode for closest-hit vs visibility,
- hit/visibility outputs,
- data widths and numeric representation,
- datapath,
- control/FSM,
- object iteration,
- nearest-hit reduction,
- square-root handling,
- buffers/storage,
- latency and throughput assumptions,
- hardware/software boundary,
- block diagram,
- performance/area/power/precision trade-offs.

Keep estimated frequency/throughput clearly labeled as estimates.

### Prompt 18 — Implement and verify the SystemVerilog design

Implement the current v1 accelerator under `Project/subRay/hw/rtl/` with modules such as:
- `fxp_sqrt.sv`,
- `sphere_intersect.sv`,
- `intersect_accel.sv`.

Use Q16.16 fixed-point arithmetic in the implemented design.

Create self-checking testbenches under `Project/subRay/hw/tb/` for:
- square-root behavior,
- sphere hit/miss cases,
- nearest-hit behavior,
- visibility mode,
- reset/control,
- repeated requests.

Run ModelSim where available and preserve compile/simulation logs.

Do not claim synthesis timing, area, power, or real FPGA speedup.

### Prompt 19 — Define the HW/SW interface

Explain how the optimized Raytrace software would use the accelerator.

Document:
- which software routines map to closest-hit and visibility modes,
- conversion from Python floats to accelerator format,
- scene loading,
- ray submission,
- `start`, `busy`, `done`, and result signaling,
- the currently implemented direct RTL ports,
- proposed MMIO register map,
- proposed buffering/DMA for batching rays,
- Python/C wrapper or driver needs,
- communication overhead.

Clearly separate **IMPLEMENTED** from **PROPOSED** integration.

### Prompt 20 — Estimate hardware performance conservatively

Use measured software data and simulated RTL behavior as the evidence base.

Apply Amdahl’s Law only with clearly labeled assumptions:

`Speedup = 1 / ((1-P) + P/S)`

If the exact intersection fraction is not directly isolated, use a justified range for `P` rather than fake precision.

Separate:
- **MEASURED SOFTWARE**,
- **SIMULATED RTL**,
- **ESTIMATED HARDWARE**,
- **PROPOSED SYSTEM INTEGRATION**.

Discuss batching, transfer overhead, latency, throughput, memory bandwidth, area, power, and precision.

## Verification performed by us

- Original Raytrace source was preserved separately.
- Software attempts were checked against deterministic rendered output for the tested scene/resolution.
- Performance was measured using saved benchmark/profiling artifacts rather than AI-generated values.
- `perf`, py-spy, and flame-graph artifacts were preserved.
- Official result: original `81.285 s` vs final Attempt 1 `19.7062 s`, approximately `4.12×` speedup / `75.76%` runtime improvement.
- Later non-fast perf-stat measurements showed Attempt 3 slightly faster than Attempt 1, but Attempt 1 remains the locked official final.
- Implemented RTL is the iterative Q16.16 v1 accelerator.
- ModelSim verification passed the recorded RTL checks.
- No synthesis, place-and-route, physical FPGA measurement, measured area, measured power, or measured hardware speedup is claimed.
