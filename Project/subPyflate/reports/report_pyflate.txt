1. OVERVIEW
================================================================================

1.1 Purpose of the benchmark
----------------------------
pyflate times a pure-Python bzip2 decoder - originally written by Paul
Sladen - decompressing one fixed input file. There is no zlib, no bz2
module, no C extension anywhere in the timed path: bit-level field reads,
Huffman table construction, the move-to-front transform, the inverse
Burrows-Wheeler transform, and the final run-length expansion are all
plain Python.

This gives pyflate a very different performance signature from a
benchmark like raytrace. raytrace's cost is spread thin across many
small, cheap object allocations; pyflate's cost concentrates in a
handful of tight, repeatedly-executed loops operating on primitive data
(bits, bytes, small integers) rather than custom objects. Pairing the two
benchmarks in this project was deliberate: they stress CPython in close
to opposite ways - allocation/dispatch overhead on one side, raw
byte-level loop throughput on the other.

Unlike raytrace, this benchmark checks its own output: at the end of
every timed iteration it computes the MD5 digest of the decompressed
result and asserts it equals a hard-coded reference digest
(afa004a630fe072901b1d9628b960974). A broken optimization does not just
run slower - it throws inside the benchmark itself. This project's own
correctness checks (2.1, Section 3) add an independent, external
byte-for-byte comparison against the preserved original on top of that
internal gate, since passing the internal MD5 check alone does not
guarantee every intermediate step behaves identically to the original.

      (this is the size of the BWT-encoded block content itself, before

       the RLE pass's own expansion behavior, which this instrumentation
       does not isolate)

    readbits() calls (bit-level field reads) .... 313,416
      total bits consumed ...................... 1,080,992

Two things stand out. First, find_next_symbol is called 296,542 times to
decode a file that is only 67,562 bytes compressed - roughly 4.4 symbol
lookups per compressed byte, and each lookup (in the original
implementation) is a linear scan of a Huffman table. Second,
move_to_front is called 185,606 times, and the original implementation
of that function rebuilds its entire list on every call via three
concatenated slices (1.5(d)), so each of those 185,606 calls performs up
to three separate list allocations.

1.3 Libraries and dependencies
------------------------------

Standard library only:

  hashlib   - hashlib.md5() computes the digest used for the benchmark's
              own internal correctness gate, checked once per loop
              against the fixed reference value.

  os, struct - path handling for locating the input file, and (in the
              unused gzip path) struct-based header parsing.

No third-party decompression library is used or available to the timed
code - zlib and the standard library's own bz2 module exist elsewhere in
CPython but are never imported here. Every bit of decompression logic
(bit reading, Huffman decoding, MTF, inverse BWT, RLE) is the benchmark's
own Python code.

Measurement and profiling tools:

  pyperf         - registers the benchmark via bench_time_func() and
                   supplies the CLI harness this project always invokes
                   through -m pyperformance run.
  pyperformance  - discovers, launches and manages bm_pyflate as one of
                   its bundled benchmarks.
  perf           - sampled hotspot profiling (Section 2.3).
  py-spy         - supplemental Python-frame flame graphs (Section 2.3).

1.4 Program structure and execution flow
-------------------------------------------

One timed loop:

  bench_pyflake(loops, filename)
    open the input file
    start timer

    repeat loops times:
      seek input to position 0
      wrap it in an RBitfield (bit-level reader)
      read a 16-bit magic number
      magic == 0x425a (bzip2)?
        bzip2_main(field)
          read method byte ('h' expected), block-size digit
          loop over compressed blocks:
            read a 48-bit block-type marker
            block-type == pi (0x314159265359)?
              decode_huffman_block(b, out)
                read the randomised-block flag (never set by this input)
                read the BWT origin pointer
                compute_used(b)          - 256-bit symbol-presence map
                read huffman_groups (2 to 6 for this format)
                compute_selectors_list(b, huffman_groups)
                compute_tables(b, huffman_groups, symbols_in_use)
                main decode loop:
                  every 50 symbols, switch to the next selected table
                  find_next_symbol(b, reversed=False)
                  RUNA/RUNB (0 or 1)? accumulate a run-length, continue
                  end-of-block symbol? stop the loop
                  otherwise: look up the byte via the favourites list,
                    move_to_front(favourites, index), append to buffer
                bwt_reverse(b"".join(buffer), pointer)
                run-length-decode the result into out[]
            block-type == sqrt(pi) (0x177245385090)?
              stream end reached, stop the block loop
          return the joined output bytes
      magic == 0x1f8b (gzip)? gzip_main(field)   (present, never reached
        by this project's input - see 1.8)

    stop timer
    assert md5(out) == the fixed reference digest
    return the elapsed time

The two decoded bzip2 blocks account for essentially all of the work
measured in 1.2 - block-type parsing and the outer loop itself are
negligible against 296,542 Huffman lookups and 185,606 MTF calls.

1.5 Algorithms
---------------

(a) Bit-level input

RBitfield reads the compressed stream through readbits(n), pulling
individual bits out of a byte buffer, most-significant-bit first. Every
piece of the bzip2 format - the block header, the Huffman group count,
the tables themselves, and every symbol code - is read this way. 313,416
calls consume 1,080,992 bits from a 67,562-byte (540,496-bit) input: the
compressed stream is read close to twice over in bit-sized pieces, a
direct consequence of decoding variable-length Huffman codes one field at
a time rather than in larger batches.

(b) Huffman table construction

compute_tables() builds one HuffmanTable per active Huffman group (2 to 6
of them per block; this file's two blocks build 12 in total) from the
per-symbol code-length data read out of the stream. Each table stores its
entries - (code, bit-length, symbol, reverse_symbol) - as HuffmanLength
objects in a plain Python list, sorted by (bits, code).

(c) Huffman symbol lookup

find_next_symbol() walks that sorted list linearly. For each candidate
entry it "peeks" (snoopbits) the right number of bits from the field and
compares against the entry's code, re-peeking only when the required bit
count changes from the previous entry. The first match consumes those
bits (readbits) and returns the decoded symbol. With 296,542 calls
against tables holding up to a few hundred entries each, this scan is the
single largest contributor to the symbol-lookup cost identified in
Section 2.

Past the point where this scan can succeed or fail, the function's source
contains a second, unreachable block: an alternate table-search loop,
never executed because the preceding code always either returns from
inside the first loop or raises immediately after it. That dead code
itself calls raise on a bare string rather than an Exception instance -
invalid in Python 3, which requires exceptions to derive from
BaseException. It is harmless precisely because it can never run, but it
is recorded here as a real, verifiable property of the source rather than
corrected, since fixing dead code has no effect on behavior or
performance (1.8).

(d) Move-to-front decoding

Bzip2's MTF stage keeps a list of "favourite" byte values. Decoding a
literal symbol looks up favourites[r-1], then calls
move_to_front(favourites, r-1) to bring that value to the front of the
list, biasing future lookups toward recently-seen bytes. The original
implementation does this with l[:] = l[c:c+1] + l[0:c] + l[c+1:] - three
list slices concatenated into a new list, assigned back over the
original - rather than a single in-place rotation. Called 185,606 times,
this is one of the clearest, most mechanical inefficiencies identified in
this report (Section 2, Section 3).

(e) Inverse Burrows-Wheeler transform

bwt_reverse() undoes the block sort applied during compression, using the
origin pointer read from the stream to walk the permutation back to the
original symbol order. This project's instrumentation confirms it runs
exactly twice (once per block) and processes 672,368 characters combined
- a single linear pass per block, not the quadratic behavior some naive
BWT implementations exhibit.

(f) Run-length decoding

The final step in decode_huffman_block scans the BWT-reversed buffer for
runs of four identical bytes; when it finds one, the following byte is
read as a count and the run is expanded by that many additional
repetitions before continuing. Any byte not starting a four-byte run is
copied through unchanged. This is a straightforward linear scan, but it
allocates a new bytes slice per iteration via list.append(), rather than
writing into a preallocated buffer (Section 2, Section 3).

(g) Block and stream framing

Two 48-bit magic constants delimit the format: one marks "another
compressed block follows," the other marks "end of stream." Between
blocks the code reads and discards a 32-bit CRC without verifying it -
the benchmark's own correctness gate is the whole-file MD5 check, not a
per-block CRC comparison.

(h) The unused gzip path

gzip_main() implements DEFLATE decoding using the same HuffmanTable
machinery, selected only when the input's magic number is 0x1f8b. The
shipped input begins with 0x425a (bzip2), so this path exists in the
source but contributes zero calls to any measurement in this report.

1.6 Main data structures
--------------------------

  RBitfield          Wraps the input file object; readbits()/snoopbits()
                     pull and peek bits from it. Every one of the
                     313,416 readbits() calls in 1.2 goes through this
                     class.

  HuffmanLength       One instance per Huffman code: code, bit-length,
                     symbol, and a precomputed bit-reversed form of the
                     code. 12 HuffmanTable instances (1.5(b)) each hold a
                     list of these.

  HuffmanTable.table  A plain Python list of HuffmanLength objects,
                     sorted by (bits, code); scanned linearly by
                     find_next_symbol() (1.5(c)).

  favourites          A Python list of the byte values in use in the
                     current block, reordered on every literal symbol by
                     move_to_front() - 185,606 rebuild operations across
                     the file (1.5(d)).

  buffer / out        Plain Python lists of byte strings, joined with
                     b"".join(...) at block and stream boundaries rather
                     than concatenated incrementally.

1.7 Candidate costs to investigate
--------------------------------------

Reading the code alongside the measured counts in 1.2 points at several
concrete places to check against a real profile:

  H1. The Huffman symbol-lookup scan
      296,542 calls to find_next_symbol, each a linear walk over a
      sorted table of HuffmanLength entries. With no upper bound faster
      than table size, this is the highest-frequency operation in the
      whole decode.

  H2. Move-to-front's three-slice rebuild
      185,606 calls, each reconstructing the entire favourites list from
      three concatenated slices (1.5(d)) instead of rotating it in
      place - real, mechanical, repeated allocation on a hot path.

  H3. The inverse-BWT working set
      672,368 characters processed by bwt_reverse across two calls;
      worth checking whether its own loop, or the list/pointer
      structures it builds, show up as a meaningful profiled cost.

  H4. Run-length-decode allocation pattern
      The final decode step (1.5(f)) builds its output via repeated
      list.append() of byte slices rather than writing into one
      preallocated buffer.

  H5. Bit-field read granularity
      313,416 readbits() calls consuming 1,080,992 bits - about twice
      the input's raw bit count - reflects decoding one Huffman field at
      a time; worth checking whether the per-call overhead of
      RBitfield.readbits() itself is measurable against this volume of
      calls.

  H6. python3-dbg's own bookkeeping
      Profiling this benchmark necessarily uses the debug interpreter
      build (for reliable perf symbol resolution); its extra
      allocation-safety checks add their own, non-application overhead
      that needs to be distinguished from real algorithmic cost when
      reading the profile (Section 2).

1.8 Relevant implementation limitations
-------------------------------------------

  - The benchmark has a genuine internal correctness gate - an MD5 check
    against a fixed reference digest - unlike raytrace, which has none.
    This project's own SHA-256/byte-for-byte external check (2.1,
    Section 3) still adds value on top of it, since passing the final
    MD5 does not by itself prove every intermediate transform behaves
    identically to the original.

  - decode_huffman_block() explicitly does not support "randomised"
    bzip2 blocks: if that flag is ever set, it executes
    raise "Bzip2 randomised support not implemented" - a bare string,
    not an Exception instance, which is invalid in Python 3 and would
    itself raise TypeError rather than deliver the intended message.
    This project's shipped input never sets that flag, so the path is
    never exercised; it is left exactly as written, since correcting it
    would touch code outside the scope of a performance optimization
    and has no bearing on this file's decode.

  - find_next_symbol() contains a second, structurally unreachable
    table-search loop after its real implementation (1.5(c)), itself
    containing the same bare-string raise pattern. It is dead code -
    verified by the fact this project's instrumentation, wrapping every
    call to the method, never observes it execute - and is left in
    place for the same reason as the item above.

  - The gzip decoding path (1.5(h)) is present in the source but
    unreachable for this project's fixed bzip2 input; no measurement in
    this report exercises it, and no optimization in Section 3 touches
    it.

  - CRC values are read from the compressed stream between blocks but
    never checked against the decoded content (1.5(g)); the only
    correctness signal the original benchmark relies on is the
    whole-file MD5 comparison at the very end.

2.4 Identified bottlenecks
------------------------------

  1. Interpreter dispatch (22.81% self time)
     Every opcode in every one of the 296,542 find_next_symbol calls and
     185,606 move_to_front calls passes through
     _PyEval_EvalFrameDefault. Confirms H1 and H5.

  2. move_to_front's list-slice churn (list_dealloc + list_ass_slice,
     4.29% combined)
     Directly measured, directly attributable to the three-slice rebuild
     in 1.5(d)/H2 - one of the clearest, most mechanically-fixable costs
     identified in either benchmark in this project.

  3. python3-dbg's own overhead (_PyMem_DebugCheckAddress, 4.06%)
     Inherent to profiling with the debug build for reliable symbol
     resolution (H6); would not appear under a release interpreter and
     is not a target for optimization.

  4. Native/library-level cost (__memset, pthread_getspecific,
     read_size_t, combined ~7.8%)
     Mostly memory-management and libc bookkeeping beneath CPython's own
     allocator; not directly attackable from the benchmark's Python
     source.

The clearest, most concrete target from this profile is item 2 - unlike
item 1, which is fundamental dispatch cost, item 2 is a specific,
correctable inefficiency in one function.


================================================================================
3. OPTIMIZATIONS
================================================================================

Unlike raytrace's three independent attempts, pyflate's three attempts
are cumulative - each builds on the previous one's code rather than
starting fresh from the original. This is recorded explicitly since it
is a different methodology from the other benchmark in this project.

3.1 Attempt 1 - Canonical Huffman LUT
------------------------------------------
Strategy: replace find_next_symbol()'s linear scan (H1) with an O(1)
lookup table of size 1 << max_bits, built once per Huffman table and
indexed directly by the next max_bits bits of the stream, in both
bit-orderings the format requires (reversed=True for gzip/LSB-first,
reversed=False for bzip2/MSB-first as used by this input). Falls back to
the original scan on a lookup miss.

Correctness: IDENTICAL=YES, MATCHES_REFERENCE=YES
(results/attempt1/correctness_report.txt).

3.2 Attempt 2 - MTF / BWT / int2byte cleanup (builds on Attempt 1)
------------------------------------------------------------------------
Strategy: directly targets H2, H3 and H4.
  - move_to_front(l, c) rewritten as l.insert(0, l.pop(c)) - one pop and
    one insert instead of three list-slice concatenations.
  - bwt_transform's character-count pass consolidated into a single
    pass building base[] directly.
  - _INT2BYTE precomputed as a lookup table instead of calling int2byte()
    repeatedly.

Correctness: IDENTICAL=YES, MATCHES_REFERENCE=YES
(results/attempt2/correctness_report.txt).

3.3 Attempt 3 - Hot-loop attribute hoisting + memoryview RLE (builds on
Attempt 2)
------------------------------------------------------------------------
Strategy: targets H5 and H4's allocation pattern directly.
  - Hoists t.find_next_symbol, favourites.pop, favourites.insert,
    buffer.append and _INT2BYTE to local variables inside
    decode_huffman_block, removing repeated attribute lookups from the
    hottest loop in the benchmark.
  - Rewrites the end-of-block run-length decode (1.5(f)) to index
    directly into the post-BWT bytes object rather than building output
    through repeated small slice allocations.

Correctness: IDENTICAL=YES, MATCHES_REFERENCE=YES
(results/attempt3/correctness_report.txt).

3.4 Selection
----------------
Attempt 3 (which includes Attempts 1 and 2's changes, being cumulative)
was selected as the official final implementation - both the preliminary
Windows sweep and the official VM measurement (Section 4) agree it is the
fastest of the three, which is a materially different situation from
raytrace, where the fastest-looking attempt in a quick preliminary test
turned out not to be the fastest at full scale. No such discrepancy
exists here; Attempt 3/Final's selection is consistent across every
measurement in this project's records.

One genuine finding worth recording rather than smoothing over: Attempt
1 alone (the LUT, before Attempts 2/3's cleanup) behaves differently
depending on how it is measured. Under pyperformance's calibrated,
warmed-up loop it is a clean win (Section 4.3). Under a cold,
per-call time.perf_counter() measurement (results/windows_preliminary.txt)
it is a regression, because building the LUT itself - up to 2**max_bits
entries per Huffman group, in pure Python - costs more than the scan it
replaces on a single cold decode. Attempts 2 and 3 remove enough
surrounding interpreter overhead that the LUT's advantage holds under
both measurement styles. This split is one of the concrete pieces of
evidence motivating hardware acceleration of the same lookup (Section 5):
a hardware LUT has O(1) load time as well as O(1) lookup, which a
pure-Python LUT does not.

3.5 Optimizations considered and not adopted
--------------------------------------------------
  - Replacing the decoder with the standard library's own bz2 module was
    not adopted, since it would move the studied computation entirely
    out of the code being measured - the point of this project is
    optimizing the given Python implementation, not substituting a
    different one.
  - A C-extension rewrite of the hot loop was not pursued, for the same
    reason: it would stop measuring Python-level optimization and start
    measuring a different implementation language.

4.2 perf stat hardware-counter comparison
-----------------------------------------------

  Metric               Baseline           Final              % change
  Elapsed               120.99 s           76.307 s            -36.93%
  task-clock             113,777 msec       76,417 msec         -32.84%
  Instructions          579,459,257,273    388,984,213,555      -32.87%
  Branches              142,417,577,761     94,689,052,878      -33.51%
  Branch-misses            770,743,225        479,262,450       -37.82%

  Page-faults                   463,011            458,789        -0.91%
  Context-switches                3,089              2,888        -6.51%

Interpretation:
  - Instructions, branches and branch-misses all fall by roughly a
    third - consistent with removing interpreter-level work (the LUT
    replacing a linear scan, fewer list allocations in move_to_front)
    rather than restructuring memory access patterns.
  - Elapsed time falls MORE (-36.93%) than raw instruction count
    (-32.87%): the remaining instructions also execute with better
    branch prediction (branch-misses fall harder than branches
    themselves, -37.82% vs -33.51%).
  - Cache-misses are essentially flat (+1.47%, within noise): the
    working set was already cache-resident before optimization: this is
    a CPU-side win (fewer instructions/branches), not a memory-side one.
    The cache-miss RATE rises (misses/references) purely because the
    denominator (references) dropped while the numerator (misses)
    stayed constant - the same pattern documented for raytrace in the
    sibling report, not a new phenomenon.
  - Page-faults and context-switches are within noise: no meaningful
    change in memory-allocation volume or scheduling behavior.

Hardware-counter caveat: the cycles counter reports exactly 0 due to a
KVM-specific PMU limitation on this host (Xeon E5-2630 v3) - every other
hardware counter above (instructions, branches, branch-misses,
cache-references, cache-misses) is exposed and was captured normally.
This is the same class of host-level PMU quirk documented for the
raytrace project on the same kind of machine, not specific to pyflate.

Two things worth spelling out precisely, since perf report percentages
are relative shares of each run's own samples, not absolute time:

  - _PyEval_EvalFrameDefault's share rises (22.81% to 24.26%), which is
    the same concentration effect documented for raytrace: 22.81% of
    120.99s baseline is about 27.6s in that symbol; 24.26% of 76.307s
    final is about 18.5s - a real ~33% absolute drop, in line with the
    overall instruction-count decrease (4.2), even though the percentage
    share went up because the total pie shrank faster than this one
    slice did.
  - list_dealloc and list_ass_slice drop out of the top 15 entirely in
    the final profile. This is not a share redistribution to explain
    away - it is the direct, measured disappearance of the exact cost
    that Attempt 2's move_to_front rewrite (3.2) targeted. Of every
    result in either benchmark's profiling data, this is the cleanest
    single before/after confirmation that a specific code change fixed
    the specific cost it was aimed at.

The remaining symbols that grew slightly as a share
(_PyMem_DebugCheckAddress, read_size_t, call_function, pthread_getspecific)
are python3-dbg's own bookkeeping and CPython's call/memory machinery -
not application code, and not addressable by further changes to
run_benchmark.py.


================================================================================
5. HARDWARE ACCELERATION PROPOSAL
================================================================================

5.1 Choice of component
---------------------------
Section 2.4 and Section 4.4 agree on where the cost concentrates:
interpreter dispatch driven by 296,542 Huffman symbol lookups and
185,606 move_to_front calls. Of the two, the Huffman lookup was selected
as the hardware target:

  - It is the higher-frequency operation (296,542 vs. 185,606 calls).
  - Its software fix (Attempt 1's LUT) demonstrated the right shape of
    solution - direct table lookup instead of a scan - but also
    demonstrated software's own limitation (3.4): building a
    2**max_bits-entry LUT in pure Python is itself expensive, which is
    exactly the load-time cost a hardware BRAM-based LUT does not pay in
    the same way.
  - move_to_front (Attempt 2's target) was already fixed cheaply and
    completely in software (4.4 shows its cost simply vanishing); there
    is little marginal benefit left to accelerate in hardware.

Bit management (RBitfield's readbits/snoopbits, 313,416 calls consuming
1,080,992 bits) maps naturally onto a small hardware barrel shifter,
and was included as a supporting component alongside the lookup itself.

5.2 Function
----------------
Two RTL modules implement this pairing directly:

  bit_shifter    Barrel-shifter FSM matching RBitfield's readbits()/
                 snoopbits() behavior: peek or consume N bits from a
                 shift register fed by the compressed byte stream.

  huff_lut       Direct-indexed lookup table matching find_next_symbol()'s
                 O(1) fast path: given the next max_bits bits (from
                 bit_shifter), returns the decoded symbol and its true
                 bit-length in one operation, in either bit-ordering the
                 format requires.

  huffman_decoder  Top-level module combining both: drives bit_shifter to
                 fill the lookup window, queries huff_lut, and reports
                 the decoded symbol back to a controlling process.

5.3 Architecture
--------------------
Implemented as three SystemVerilog modules under Project/subPyflate/hw/rtl/:
bit_shifter.sv, huff_lut.sv, and huffman_decoder.sv, with matching
testbenches under Project/subPyflate/hw/tb/ and a simulator-autodetecting runner
at Project/subPyflate/hw/run_sim.sh (ModelSim, Icarus Verilog, or Verilator).

5.4 Interfaces (implemented vs. proposed)
------------------------------------------------

Implemented: direct RTL port-level interfaces on bit_shifter, huff_lut
and huffman_decoder, driven by their testbenches in simulation.

Proposed for deployment (not implemented): an MMIO register map, an
AXI4-Lite control interface paired with AXI4-Stream for the compressed
byte stream, a DMA path for bulk transfer, a Python C-extension wrapper,
a real device driver, and actual FPGA integration
(Project/subPyflate/docs/12_hw_sw_interface.md).

5.5 Simulation results
---------------------------
Simulated with Icarus Verilog 12.0 (Windows, 2026-09-21); results in
Project/subPyflate/hw/results/SIMULATION_RESULTS.txt:

  tb_huff_lut:         5 checks, 0 errors - ALL PASS
  tb_bit_shifter:      8 checks, 0 errors - ALL PASS
  tb_huffman_decoder:  9 checks, 0 errors - ALL PASS

  Total: 22 checks, 0 errors.

This demonstrates the implemented RTL's logical correctness against its
own specification; it does not measure deployed FPGA performance, area,
or power, all of which remain estimates (5.6).

5.6 Expected performance (estimated, not measured)
----------------------------------------------------------
Target clock: 200 MHz (labeled ESTIMATE, not synthesized or measured).
Estimated latency: 3 cycles per decoded symbol for the v1 design, 1
cycle per symbol for a proposed v2 pipeline (Project/subPyflate/docs/13_hardware_
performance.md). Area, power and achievable bandwidth are likewise
documented there as estimates only.

No synthesis, no FPGA bring-up, and no measured hardware-in-the-loop
timing exists for this design - the same evidence boundary maintained
throughout the raytrace hardware proposal.

5.7 Trade-offs
------------------
Load-time vs. software. The motivating finding in 3.4 is specifically a
load-time problem in software (building a large LUT in pure Python is
slow even though querying it is fast); a hardware BRAM-backed LUT is
expected to have both fast load and fast lookup, which is the core of
the acceleration argument here rather than lookup speed alone.

Area/complexity. A direct 2**max_bits-entry lookup table trades memory
(BRAM) for guaranteed O(1) access; the proposed v2 pipeline trades
additional area for one-cycle-per-symbol throughput over v1's three.

Scope. Only the Huffman lookup and its supporting bit-shifter are
targeted; move_to_front, already fixed cheaply in software (4.4), is
deliberately left out of the hardware proposal rather than accelerated
redundantly.


================================================================================
6. CONCLUSION
================================================================================

pyflate measures a pure-Python bzip2 decoder against a fixed 67,562-byte
input, decompressing to 399,360 bytes. Unlike raytrace's many small
object allocations, its cost concentrates in a small number of
repeatedly-executed loops over primitive data: 296,542 Huffman symbol
lookups and 185,606 move-to-front calls account for the large majority of
measured interpreter work.

Profiling confirmed two concrete, separately-addressable costs:
interpreter dispatch overhead inherent to both hot loops (22.81% self
time), and a specific, mechanical inefficiency in move_to_front's
three-slice list rebuild, independently confirmed twice over - once by
its 4.29% combined perf share in the baseline, and again by that exact
share disappearing entirely from the final profile's top 15 symbols
after Attempt 2's fix.

Three cumulative optimization attempts were implemented and verified
correct, both by the benchmark's own internal MD5 gate and by this
project's external byte-for-byte comparison against the preserved
original. Attempt 3 (canonical Huffman LUT, plus MTF/BWT/int2byte
cleanup, plus hot-loop attribute hoisting) was selected as the official
final implementation and measured at 36.93% improvement on the official
VM (120.99s to 76.307s), corroborated by an independent 29.84% result on
a completely separate Windows/CPython 3.12 environment - both comfortably
clearing the project's 7% requirement. Unlike the raytrace report, there
is no discrepancy to disclose between preliminary and official rankings
here: Attempt 3 is the fastest attempt in every measurement taken.

Hardware counters confirm the result beyond wall-clock time: instructions
-32.87%, branches -33.51%, branch-misses -37.82%, all consistent with
removing interpreter-level dispatch and allocation work. A genuine,
non-obvious finding from the optimization process - that the Huffman LUT
is a clear win under warmed-up measurement but a measured regression
under a cold, single-decode measurement, because building the LUT itself
is expensive in pure Python - became the direct motivation for the
hardware proposal: a BRAM-backed lookup table, unlike a Python dict or
list built fresh every time, does not pay that same load-time cost. Three
SystemVerilog modules (bit-shifter, direct-indexed LUT, and a combining
decoder) were implemented and verified in simulation: 0 errors across 22
functional checks. This demonstrates logical correctness only; no
synthesis, deployment, or measured hardware performance is claimed
anywhere in this report.
